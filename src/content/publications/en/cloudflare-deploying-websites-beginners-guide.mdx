You've built a website on your computer, and now you want other people to see it. This guide explains what "putting a website online" actually involves (hosting, domains, DNS and CDNs) and then shows, step by step, how to publish a site with Cloudflare so that it updates automatically every time you push a change to GitHub.

It's written for complete beginners. If Git and GitHub are new to you, read the companion guide *GitHub: A Beginner's Guide to Git and Version Control* first, because the tutorial here starts from a GitHub repository.

## What happens when you open a website?

When someone types `example.com` into a browser, three things are needed:

1. **A domain name**, the human-friendly address, such as `example.com`. You rent it from a **registrar** for a yearly fee.
2. **DNS** (Domain Name System), which translates the name into the numeric **IP address** of a computer on the internet. It works much like a phone book.
3. **Hosting**: a computer that stores your website's files and sends them to the browser.

Large services add a fourth piece: a **CDN** (Content Delivery Network). A CDN is a network of data centres around the world that keep copies of your files close to your visitors. A reader in Tokyo then gets your page from a nearby data centre instead of from a server in Zurich, which makes it faster and spreads the load [@cf-how].

<RequestFlow />

Cloudflare can take on all of these roles: it runs DNS, operates one of the largest CDNs, and with **Workers** it can also host your site directly in its data centres. You don't need a separate server.

### Static and dynamic websites

- A **static** website consists of finished files (HTML, CSS, JavaScript, images) that are the same for every visitor. Many personal sites, blogs and documentation sites are static, including sites built with tools such as Astro, Hugo or Eleventy. They're simple, fast and cheap to host.
- A **dynamic** website creates pages on request, for example to show a user's account or search results. It needs code running on a server.

This guide focuses on static sites, the most common starting point. Workers can also run server code later, if you need it.

## Key terms

| Term | Meaning |
| --- | --- |
| **Domain** | A name such as `example.com`. A **subdomain** adds a part in front: `www.example.com`, `blog.example.com`. |
| **Registrar** | The company where you register (rent) a domain. Cloudflare is also a registrar. |
| **Nameservers** | The servers responsible for a domain's DNS. Whoever runs them controls where the domain points. |
| **DNS record** | One entry in a domain's DNS. The common types are listed below. |
| **Proxied** (orange cloud) | Traffic goes through Cloudflare's network, with caching and protection. |
| **DNS only** (grey cloud) | Cloudflare only answers the DNS question; traffic goes directly to the target. |
| **Edge** | Cloudflare's data centres close to visitors, where requests are answered. |
| **SSL/TLS** (HTTPS) | Encryption between browser and website, shown by the padlock. Cloudflare issues the certificates automatically. |
| **Deployment** | Publishing a new version of your site. |

The most common DNS record types:

| Type | Points to | Example |
| --- | --- | --- |
| `A` | An IPv4 address | `example.com → 192.0.2.10` |
| `AAAA` | An IPv6 address | `example.com → 2001:db8::10` |
| `CNAME` | Another name (an alias) | `www.example.com → example.com` |
| `TXT` | Free text, often used to prove you own a domain | `"google-site-verification=…"` |
| `MX` | The mail server for the domain | `mail.example.com` |

## Workers or Pages?

Cloudflare has two products for websites, and older tutorials mostly use the second one:

- **Workers** started as a way to run code on Cloudflare's network. With **static assets**, a Worker can also serve the files of a whole website, with or without additional code [@cf-assets].
- **Pages** was built specifically for hosting websites from a Git repository.

Cloudflare now recommends **Workers for new projects**. Its documentation states that Workers supports most Pages use cases, offers more features, and is Cloudflare's main platform for applications [@cf-pages]. Pages still works and existing Pages projects keep running, but new features arrive in Workers first.

| | Workers (with static assets) | Pages |
| --- | --- | --- |
| Status | Recommended for new projects | Supported; mainly for existing projects |
| Static websites | Yes | Yes |
| Server code | Yes, in the Worker | Yes, with Pages Functions |
| Automatic deployments from Git | Workers Builds | Built into Pages |
| Free address | `name.your-subdomain.workers.dev` | `name.pages.dev` |
| Configuration | `wrangler.jsonc` file in the repository | Mostly in the dashboard |

This guide uses **Workers**.

## Before you start

You need:

- A **GitHub account** and a repository with your website, for example `my-first-website`. Any static site works: plain HTML files, like the ones from the GitHub guide, or a site built with a tool such as Astro, where `npm run build` writes the finished files to a folder called `dist`. The steps below cover both.
- A free **Cloudflare account** from [dash.cloudflare.com](https://dash.cloudflare.com).
- **Node.js** on your computer, only if your site has a build step and you want to test it locally.

## Step 1: Add a Wrangler configuration file

Cloudflare's tools are called **Wrangler**, and they read their settings from a file in your repository. Cloudflare recommends the JSON format, `wrangler.jsonc`, for new projects [@cf-wrangler-config]. Create it in the root folder of your project:

```jsonc
// wrangler.jsonc
{
  "name": "my-first-website",
  "compatibility_date": "2026-11-16",
  "assets": {
    "directory": "./dist",
    "not_found_handling": "404-page"
  }
}
```

| Setting | What it does |
| --- | --- |
| `name` | The name of your Worker. It becomes part of the address and **must match** the name in the dashboard. |
| `compatibility_date` | Tells Cloudflare which version of the runtime to use. Set it to today's date when you create the project. |
| `assets.directory` | The folder your build writes the finished site to: `./dist` for Astro, often `./build` or `./public` for other tools. |
| `assets.not_found_handling` | `"404-page"` shows your own `404.html` for addresses that don't exist [@cf-ssg]. |

<Callout type="note" title="Just HTML files, no build step?">
  If your site is a few HTML files, like `index.html` and `contact.html` from the GitHub guide, there is nothing to build. Move these files into a folder called `public` and set `"directory": "./public"` in `wrangler.jsonc`. Keep `wrangler.jsonc` and `README.md` outside that folder, so only your website's files are published. In step 3, leave the **Build command** empty.
</Callout>

Commit and push the file:

```bash
git add wrangler.jsonc
git commit -m "Add Cloudflare configuration"
git push
```

<Callout type="note" title="No configuration file?">
  If you connect a repository without a Wrangler configuration file, Cloudflare tries to detect your framework, creates the configuration for you and opens a pull request in your repository with the changes. Once you merge it, the project deploys normally [@cf-builds]. Writing the file yourself, as above, means you know exactly what's in it.
</Callout>

- **Install** the *Cloudflare Workers & Pages* app on your GitHub account. This decides **which repositories** Cloudflare can access. Choose **Only select repositories** and pick `my-first-website` instead of giving access to everything.
- **Authorize** the app. This tells Cloudflare **who you are** on GitHub. Each person does it once.

## Step 3: Configure the build and deploy

Back in Cloudflare, select your repository and fill in the settings:

| Field | Value for this example | Explanation |
| --- | --- | --- |
| **Project name** | `my-first-website` | Must match `name` in `wrangler.jsonc`. |
| **Build command** | `npm run build` | Builds the site. Leave it empty if your repository already contains the finished files. |
| **Deploy command** | `npx wrangler deploy` | The default. Uploads the result and makes it live. |
| **Root directory** | (empty) | Only needed if the website is in a subfolder of the repository. |

Select **Save and Deploy**. Cloudflare now copies your repository, installs the packages, runs the build command and then the deploy command.

You'll find the same settings again later on every build page of your Worker. Here they are for the Worker behind this website:

## Automatic deployments

Your site is now connected to GitHub. From here on, you don't need to do anything in Cloudflare to publish changes:

<DeployPipeline />

1. Change something on your computer, commit and `git push` to `main`.
2. GitHub notifies Cloudflare.
3. **Workers Builds** builds and deploys the new version [@cf-builds-config].
4. After a minute or two, the change is live.

**Pushes to other branches** can be built as **previews**. Each one gets its own preview URL, and if the branch belongs to a pull request, Cloudflare posts the link as a comment on GitHub [@cf-github]. You can open the preview and check the change before merging it into `main`. Preview builds are switched on or off under **Settings > Build > Branch control** (**Enable Preview Builds**), where you also choose the production branch [@cf-branches].

### Seeing and undoing deployments

The **Deployments** tab of your Worker lists the active version and earlier ones, together with the commit that produced them. **Build** next to a version opens its build log.

<Screenshot
  name="cloudflare-deployments"

  caption="The Deployments tab of this website’s Worker. Each version shows the commit it was built from; versions marked Dashboard were uploaded by hand instead of being built from GitHub. The three-dot icon on the right of a version leads to Rollback."

If a new version has a problem, select the three-dot icon on the right of an earlier version and choose **Rollback**. A rollback makes the selected older version live again; it doesn't change your GitHub repository [@cf-rollbacks]. Fix the problem in your code afterwards and push again.

## Adding a custom domain

The `workers.dev` address is fine for testing, but for a real website you'll want your own domain, such as `example.com`. There are two steps.

### Step 1: Move the domain's DNS to Cloudflare

For a Custom Domain, Cloudflare needs to manage the domain's DNS: the domain must be an **active zone** in your Cloudflare account [@cf-custom-domains].

- If you **buy the domain from Cloudflare**, this is already done.
- If the domain is with **another registrar**, add it in the Cloudflare dashboard. Cloudflare shows you two nameservers. Log in at your registrar and replace its nameservers with Cloudflare's. If DNSSEC is turned on at the registrar, turn it off first; you can turn it on again through Cloudflare later [@cf-dns-setup].

The change can take **up to 24 hours**. When it's done, the domain shows as **Active** in Cloudflare and you receive an email. From then on, the domain's DNS records are managed in Cloudflare. This is what such records look like, and what the cloud icons next to them mean:

<DnsRecords />

### Step 2: Connect the domain to your Worker

1. Open **Workers & Pages** and select your Worker.
2. Open the **Domains** tab and select **Add Domain**. (In older versions of the dashboard, this was under **Settings > Domains & Routes**.)
3. Search for your domain in the dialog, select it and confirm.

<Screenshot
  name="cloudflare-custom-domain"
  alt="The Connect domain dialog in the Domains tab of a Worker in Cloudflare, with a search field for domains, the message No zones found and the buttons Cancel and Purchase Domain; behind it the empty list Custom Domains and Routes with the Add Domain button."
  caption="Connecting a domain. The dialog only lists domains that are already in your Cloudflare account. This account has none yet, so it shows No zones found and offers to buy one; that’s why step 1 comes first."
/>

Cloudflare creates the DNS record and the HTTPS certificate automatically [@cf-custom-domains]. After a few minutes, your site is available at your own domain, with the padlock in the address bar.

<Callout type="warning" title="Existing records get in the way">
  A Custom Domain can't be added to a hostname that already has a `CNAME` record. If you've set up the domain for another service before, delete the old record on the DNS page first.
</Callout>

## Alternative: deploying from the command line

Instead of the dashboard, you can create and deploy a project from the terminal. To start a new Astro project that's ready for Cloudflare [@cf-astro]:

```bash
npm create cloudflare@latest -- my-first-website --framework=astro
```

To deploy an existing project manually:

```bash
npx wrangler login     # opens the browser once to sign in
npm run build          # builds the site into ./dist
npx wrangler deploy    # uploads it and makes it live
```

This is handy for quick tests. For a real website, the GitHub connection is usually better: every version is linked to a commit, and nobody has to remember to deploy by hand.

## If you already use Pages

Existing Pages projects keep working, and the ideas in this guide are the same: connect a repository, set a build command and an output folder, and every push deploys. The main differences are that a Pages project gets a `pages.dev` address and is configured mostly in the dashboard. If you want to move a Pages project to Workers, Cloudflare provides a migration guide, linked from the Pages documentation [@cf-pages].

## Troubleshooting

Most problems show up in the **build log**. Read the last lines before the error first.

| Problem | Likely cause | What to do |
| --- | --- | --- |
| `The name in your Wrangler configuration file … must match the name of your Worker` | The project name in the dashboard and `name` in `wrangler.jsonc` differ. | Make them the same, commit and push again [@cf-builds-troubleshoot]. |
| `Missing entry-point` | Cloudflare can't find `wrangler.jsonc`. | Check that the file is in the repository's root folder, or set the **Root directory** in **Settings > Build**. |
| Build succeeds, but the site shows a 404 or a blank page | `assets.directory` doesn't point to the folder your build creates, or the build command is missing. | Compare `assets.directory` with your framework's output folder and check the build command [@cf-builds-troubleshoot]. |
| Unknown addresses show an empty page instead of your 404 page | `not_found_handling` isn't set. | Add `"not_found_handling": "404-page"` to `assets` [@cf-ssg]. |
| `npm ci` says `package.json` and `package-lock.json` are out of sync | The lock file wasn't updated or committed. | Run `npm install` locally and commit `package-lock.json`. |
| The build uses the wrong Node.js version | The build image uses its default version. | Add a `.node-version` or `.nvmrc` file, or set the build variable `NODE_VERSION`. |
| A variable is missing during the build | It was set as a runtime variable. | **Build** variables go under **Settings > Build**; runtime variables under **Settings > Variables & Secrets**. |
| The domain stays **Pending** | The nameservers haven't been changed yet, or the change is still in progress. | Check the nameservers at your registrar and wait up to 24 hours [@cf-dns-setup]. |
| `ERR_TOO_MANY_REDIRECTS` | Usually the SSL/TLS encryption mode conflicts with redirects on your own server. | Follow Cloudflare's guide to this error [@cf-redirects]. A site served entirely by a Worker is rarely affected. |
| The old version still appears | The browser shows a cached copy, or the latest build failed. | Reload with <kbd>Ctrl</kbd>+<kbd>Shift</kbd>+<kbd>R</kbd> (<kbd>Cmd</kbd>+<kbd>Shift</kbd>+<kbd>R</kbd> on macOS) and check the status of the latest build. |

## Conclusion

Putting a website online means combining a domain, DNS and hosting, and Cloudflare can handle all three. For new projects, Cloudflare recommends Workers: a small `wrangler.jsonc` file describes your site, the GitHub connection builds and deploys every push automatically, and a custom domain takes a few clicks once your DNS is on Cloudflare. When something goes wrong, the build log and the Deployments tab tell you what happened, and a rollback brings back an earlier version while you fix the problem.
