Du hast eine Website auf deinem Computer gebaut und möchtest, dass andere sie sehen. Dieser Leitfaden erklärt, was «eine Website online stellen» eigentlich bedeutet (Hosting, Domains, DNS und CDNs), und zeigt dann Schritt für Schritt, wie du eine Website mit Cloudflare veröffentlichst. Am Ende aktualisiert sie sich jedes Mal automatisch, wenn du eine Änderung auf GitHub pushst.

Der Leitfaden richtet sich an Einsteigerinnen und Einsteiger ohne Vorwissen. Sind dir Git und GitHub noch neu, lies zuerst den Leitfaden *GitHub: Einstieg in Git und Versionskontrolle*, denn das Tutorial hier beginnt mit einem GitHub-Repository.

## Was passiert, wenn du eine Website aufrufst?

Tippt jemand `example.com` in den Browser, braucht es drei Dinge:

1. **Einen Domainnamen**, die gut lesbare Adresse wie `example.com`. Du mietest ihn gegen eine jährliche Gebühr bei einem **Registrar**.
2. **DNS** (Domain Name System), das den Namen in die **IP-Adresse** eines Computers im Internet übersetzt, ähnlich wie ein Telefonbuch.
3. **Hosting**: einen Computer, der die Dateien deiner Website speichert und an den Browser schickt.

Grössere Dienste ergänzen ein viertes Element: ein **CDN** (*Content Delivery Network*). Das ist ein Netz von Rechenzentren auf der ganzen Welt, die Kopien deiner Dateien in der Nähe deiner Besucherinnen und Besucher bereithalten. Wer in Tokio liest, bekommt deine Seite dann aus einem nahen Rechenzentrum statt von einem Server in Zürich. Das macht sie schneller und verteilt die Last [@cf-how].

<RequestFlow />

Cloudflare kann all diese Aufgaben übernehmen: Es betreibt DNS, eines der grössten CDNs und kann deine Website mit **Workers** auch direkt in seinen Rechenzentren hosten. Einen eigenen Server brauchst du nicht.

### Statische und dynamische Websites

- Eine **statische** Website besteht aus fertigen Dateien (HTML, CSS, JavaScript, Bilder), die für alle gleich sind. Viele persönliche Websites, Blogs und Dokumentationen sind statisch, auch solche, die mit Werkzeugen wie Astro, Hugo oder Eleventy gebaut werden. Sie sind einfach, schnell und günstig zu hosten.
- Eine **dynamische** Website erzeugt Seiten erst bei der Anfrage, etwa um ein Benutzerkonto oder Suchergebnisse anzuzeigen. Dafür braucht es Code, der auf einem Server läuft.

Dieser Leitfaden konzentriert sich auf statische Websites, den häufigsten Einstieg. Workers kann später bei Bedarf auch Servercode ausführen.

## Die wichtigsten Begriffe

| Begriff | Bedeutung |
| --- | --- |
| **Domain** | Ein Name wie `example.com`. Eine **Subdomain** setzt etwas davor: `www.example.com`, `blog.example.com`. |
| **Registrar** | Das Unternehmen, bei dem du eine Domain registrierst (mietest). Auch Cloudflare ist ein Registrar. |
| **Nameserver** | Die Server, die für das DNS einer Domain zuständig sind. Wer sie betreibt, bestimmt, wohin die Domain zeigt. |
| **DNS-Eintrag** | Ein einzelner Eintrag im DNS einer Domain. Die wichtigsten Typen stehen unten. |
| **Proxied** (orange Wolke) | Der Datenverkehr läuft über Cloudflares Netzwerk, mit Cache und Schutz. |
| **DNS only** (graue Wolke) | Cloudflare beantwortet nur die DNS-Anfrage; der Datenverkehr geht direkt zum Ziel. |
| **Edge** | Cloudflares Rechenzentren in der Nähe der Nutzerinnen und Nutzer, wo Anfragen beantwortet werden. |
| **SSL/TLS** (HTTPS) | Verschlüsselung zwischen Browser und Website, erkennbar am Schloss-Symbol. Cloudflare stellt die Zertifikate automatisch aus. |
| **Deployment** | Das Veröffentlichen einer neuen Version deiner Website. |

Die häufigsten DNS-Eintragstypen:

| Typ | Zeigt auf | Beispiel |
| --- | --- | --- |
| `A` | Eine IPv4-Adresse | `example.com → 192.0.2.10` |
| `AAAA` | Eine IPv6-Adresse | `example.com → 2001:db8::10` |
| `CNAME` | Einen anderen Namen (Alias) | `www.example.com → example.com` |
| `TXT` | Freien Text, oft als Nachweis, dass dir eine Domain gehört | `"google-site-verification=…"` |
| `MX` | Den Mailserver der Domain | `mail.example.com` |

## Workers oder Pages?

Cloudflare hat zwei Produkte für Websites, und ältere Anleitungen verwenden meist das zweite:

- **Workers** war ursprünglich dafür gedacht, Code in Cloudflares Netzwerk auszuführen. Mit **Static Assets** liefert ein Worker auch die Dateien einer ganzen Website aus, mit oder ohne zusätzlichen Code [@cf-assets].
- **Pages** wurde eigens dafür entwickelt, Websites aus einem Git-Repository zu hosten.

Für **neue Projekte empfiehlt Cloudflare inzwischen Workers**. Laut Dokumentation deckt Workers die meisten Anwendungsfälle von Pages ab, bietet mehr Funktionen und ist Cloudflares wichtigste Plattform für Anwendungen [@cf-pages]. Pages funktioniert weiterhin, und bestehende Projekte laufen weiter, aber neue Funktionen kommen zuerst zu Workers.

| | Workers (mit Static Assets) | Pages |
| --- | --- | --- |
| Stellenwert | Empfohlen für neue Projekte | Unterstützt; vor allem für bestehende Projekte |
| Statische Websites | Ja | Ja |
| Servercode | Ja, im Worker | Ja, mit Pages Functions |
| Automatische Deployments aus Git | Workers Builds | In Pages eingebaut |
| Kostenlose Adresse | `name.your-subdomain.workers.dev` | `name.pages.dev` |
| Konfiguration | Datei `wrangler.jsonc` im Repository | Grösstenteils im Dashboard |

Dieser Leitfaden verwendet **Workers**.

## Das brauchst du

- Ein **GitHub-Konto** und ein Repository mit deiner Website, zum Beispiel `my-first-website`. Jede statische Website eignet sich: einfache HTML-Dateien wie die aus dem GitHub-Leitfaden oder eine Website, die mit einem Werkzeug wie Astro gebaut wird; dort legt `npm run build` die fertigen Dateien im Ordner `dist` ab. Die Schritte unten decken beides ab.
- Ein kostenloses **Cloudflare-Konto** auf [dash.cloudflare.com](https://dash.cloudflare.com).
- **Node.js** auf deinem Computer, nur falls deine Website einen Build-Schritt hat und du ihn lokal testen willst.

## Schritt 1: Wrangler-Konfiguration anlegen

Die Werkzeuge von Cloudflare heissen **Wrangler** und lesen ihre Einstellungen aus einer Datei in deinem Repository. Für neue Projekte empfiehlt Cloudflare das JSON-Format `wrangler.jsonc` [@cf-wrangler-config]. Lege die Datei im Hauptordner deines Projekts an:

```jsonc
// wrangler.jsonc
{
  "name": "my-first-website",
  "compatibility_date": "2026-11-16",
  "assets": {
    "directory": "./dist",
    "not_found_handling": "404-page"
  }
}
```

| Einstellung | Was sie bewirkt |
| --- | --- |
| `name` | Der Name deines Workers. Er wird Teil der Adresse und **muss** mit dem Namen im Dashboard **übereinstimmen**. |
| `compatibility_date` | Legt fest, welche Version der Laufzeitumgebung Cloudflare verwendet. Trag beim Anlegen des Projekts das heutige Datum ein. |
| `assets.directory` | Der Ordner, in den dein Build die fertige Website schreibt: `./dist` bei Astro, bei anderen Werkzeugen oft `./build` oder `./public`. |
| `assets.not_found_handling` | `"404-page"` zeigt bei Adressen, die es nicht gibt, deine eigene `404.html` [@cf-ssg]. |

<Callout type="note" title="Nur HTML-Dateien, ohne Build?">
  Besteht deine Website aus ein paar HTML-Dateien, etwa `index.html` und `contact.html` aus dem GitHub-Leitfaden, gibt es nichts zu bauen. Verschiebe diese Dateien in einen Ordner `public` und trage in `wrangler.jsonc` `"directory": "./public"` ein. `wrangler.jsonc` und `README.md` bleiben ausserhalb dieses Ordners, damit nur die Dateien deiner Website veröffentlicht werden. In Schritt 3 lässt du den **Build command** leer.
</Callout>

Committe und pushe die Datei:

```bash
git add wrangler.jsonc
git commit -m "Add Cloudflare configuration"
git push
```

<Callout type="note" title="Keine Konfigurationsdatei?">
  Verbindest du ein Repository ohne Wrangler-Konfiguration, versucht Cloudflare, dein Framework zu erkennen, erstellt die Konfiguration selbst und öffnet dafür einen Pull Request in deinem Repository. Sobald du ihn zusammenführst, wird das Projekt normal veröffentlicht [@cf-builds]. Schreibst du die Datei wie oben selbst, weisst du genau, was drinsteht.
</Callout>

## Schritt 3: Build und Deployment einrichten

Zurück bei Cloudflare wählst du dein Repository und füllst die Einstellungen aus:

| Feld | Wert in diesem Beispiel | Erklärung |
| --- | --- | --- |
| **Project name** | `my-first-website` | Muss mit `name` in `wrangler.jsonc` übereinstimmen. |
| **Build command** | `npm run build` | Baut die Website. Leer lassen, wenn dein Repository die fertigen Dateien schon enthält. |
| **Deploy command** | `npx wrangler deploy` | Die Voreinstellung. Lädt das Ergebnis hoch und schaltet es live. |
| **Root directory** | (leer) | Nur nötig, wenn die Website in einem Unterordner des Repositorys liegt. |

Wähle **Save and Deploy**. Cloudflare kopiert nun dein Repository, installiert die Pakete, führt den Build-Befehl und danach den Deploy-Befehl aus.

Dieselben Einstellungen findest du später auf jeder Build-Seite deines Workers wieder. So sehen sie beim Worker dieser Website aus:

## Automatische Deployments

Deine Website ist jetzt mit GitHub verbunden. Um Änderungen zu veröffentlichen, musst du bei Cloudflare nichts mehr tun:

<DeployPipeline />

1. Du änderst etwas auf deinem Computer, committest und machst `git push` auf `main`.
2. GitHub benachrichtigt Cloudflare.
3. **Workers Builds** baut und veröffentlicht die neue Version [@cf-builds-config].
4. Nach ein, zwei Minuten ist die Änderung live.

**Pushes auf andere Branches** lassen sich als **Vorschau** (*Preview*) bauen. Jede bekommt eine eigene Vorschau-URL, und gehört der Branch zu einem Pull Request, schreibt Cloudflare den Link als Kommentar auf GitHub [@cf-github]. So kannst du die Änderung ansehen, bevor du sie in `main` zusammenführst. Vorschau-Builds schaltest du unter **Settings > Build > Branch control** (**Enable Preview Builds**) ein oder aus; dort legst du auch den Produktions-Branch fest [@cf-branches].

### Deployments ansehen und rückgängig machen

Der Tab **Deployments** deines Workers zeigt die aktive Version und frühere Versionen, jeweils mit dem Commit, aus dem sie entstanden sind. **Build** neben einer Version öffnet ihr Build-Protokoll.

<Screenshot
  name="cloudflare-deployments"
  alt="Der Tab Deployments des Workers jasmin-research bei Cloudflare: oben das aktive Deployment mit seiner Versions-ID, darunter fünf Versionen, jeweils mit Commit-Nachricht, Status Ready, Quelle (Build oder Dashboard), Branch, Urheber, Zeit und einem Drei-Punkte-Symbol rechts."

Hat eine neue Version ein Problem, wählst du das Drei-Punkte-Symbol rechts neben einer früheren Version und dann **Rollback**. Dabei wird die gewählte ältere Version wieder live geschaltet; dein GitHub-Repository bleibt unverändert [@cf-rollbacks]. Behebe den Fehler danach im Code und pushe erneut.

## Eine eigene Domain verbinden

Die `workers.dev`-Adresse genügt zum Testen. Für eine richtige Website möchtest du aber eine eigene Domain wie `example.com`. Dafür sind zwei Schritte nötig.

### Schritt 1: Das DNS der Domain zu Cloudflare umziehen

Für eine Custom Domain muss Cloudflare das DNS der Domain verwalten: Die Domain muss in deinem Cloudflare-Konto als **aktive Zone** eingetragen sein [@cf-custom-domains].

- **Kaufst du die Domain bei Cloudflare**, ist das bereits erledigt.
- Liegt die Domain bei **einem anderen Registrar**, fügst du sie im Cloudflare-Dashboard hinzu. Cloudflare zeigt dir zwei Nameserver an. Melde dich bei deinem Registrar an und ersetze dessen Nameserver durch die von Cloudflare. Ist dort DNSSEC aktiviert, schalte es vorher aus; du kannst es später über Cloudflare wieder einschalten [@cf-dns-setup].

Die Umstellung kann **bis zu 24 Stunden** dauern. Danach steht die Domain bei Cloudflare auf **Active**, und du bekommst eine E-Mail. Ab dann verwaltest du die DNS-Einträge der Domain bei Cloudflare. So sehen solche Einträge aus, und das bedeuten die Wolken daneben:

<DnsRecords />

### Schritt 2: Die Domain mit deinem Worker verbinden

1. Öffne **Workers & Pages** und wähle deinen Worker.
2. Öffne den Tab **Domains** und wähle **Add Domain**. (In älteren Versionen des Dashboards lag das unter **Settings > Domains & Routes**.)
3. Suche im Dialog nach deiner Domain, wähle sie aus und bestätige.

<Screenshot
  name="cloudflare-custom-domain"
  alt="Der Dialog Connect domain im Tab Domains eines Workers bei Cloudflare, mit einem Suchfeld für Domains, der Meldung No zones found und den Buttons Cancel und Purchase Domain; dahinter die leere Liste Custom Domains and Routes mit dem Button Add Domain."
  caption="Eine Domain verbinden. Der Dialog listet nur Domains, die bereits in deinem Cloudflare-Konto liegen. Dieses Konto hat noch keine, deshalb steht dort No zones found, und Cloudflare bietet an, eine zu kaufen. Darum kommt Schritt 1 zuerst."
/>

Cloudflare legt den DNS-Eintrag und das HTTPS-Zertifikat automatisch an [@cf-custom-domains]. Nach ein paar Minuten ist deine Website unter deiner eigenen Domain erreichbar, mit dem Schloss in der Adresszeile.

<Callout type="warning" title="Bestehende Einträge stehen im Weg">
  Für einen Hostnamen, der bereits einen `CNAME`-Eintrag hat, lässt sich keine Custom Domain anlegen. Hast du die Domain früher für einen anderen Dienst eingerichtet, lösche den alten Eintrag zuerst auf der DNS-Seite.
</Callout>

## Alternative: Veröffentlichen über die Kommandozeile

Statt über das Dashboard kannst du ein Projekt auch im Terminal anlegen und veröffentlichen. So startest du ein neues Astro-Projekt, das bereits für Cloudflare eingerichtet ist [@cf-astro]:

```bash
npm create cloudflare@latest -- my-first-website --framework=astro
```

Ein bestehendes Projekt veröffentlichst du von Hand so:

```bash
npx wrangler login     # öffnet einmalig den Browser zur Anmeldung
npm run build          # baut die Website in ./dist
npx wrangler deploy    # lädt sie hoch und schaltet sie live
```

Für schnelle Tests ist das praktisch. Für eine richtige Website ist die Verbindung mit GitHub meist die bessere Wahl: Jede Version ist mit einem Commit verknüpft, und niemand muss daran denken, von Hand zu veröffentlichen.

## Wenn du bereits Pages nutzt

Bestehende Pages-Projekte funktionieren weiter, und die Ideen aus diesem Leitfaden gelten genauso: Repository verbinden, Build-Befehl und Ausgabeordner festlegen, und jeder Push wird veröffentlicht. Die wichtigsten Unterschiede: Ein Pages-Projekt bekommt eine `pages.dev`-Adresse und wird grösstenteils im Dashboard eingerichtet. Möchtest du ein Pages-Projekt zu Workers umziehen, bietet Cloudflare dafür eine Anleitung, die in der Pages-Dokumentation verlinkt ist [@cf-pages].

## Fehlersuche

Die meisten Probleme zeigen sich im **Build-Protokoll**. Lies zuerst die letzten Zeilen vor dem Fehler. Die Meldungen sind auf Englisch und stehen hier im Original.

| Problem | Wahrscheinliche Ursache | Was du tust |
| --- | --- | --- |
| `The name in your Wrangler configuration file … must match the name of your Worker` | Der Projektname im Dashboard und `name` in `wrangler.jsonc` unterscheiden sich. | Beide gleich benennen, committen und erneut pushen [@cf-builds-troubleshoot]. |
| `Missing entry-point` | Cloudflare findet `wrangler.jsonc` nicht. | Prüfen, ob die Datei im Hauptordner des Repositorys liegt, oder unter **Settings > Build** das **Root directory** setzen. |
| Der Build klappt, aber die Website zeigt einen 404-Fehler oder eine leere Seite | `assets.directory` zeigt nicht auf den Ordner, den dein Build erzeugt, oder der Build-Befehl fehlt. | `assets.directory` mit dem Ausgabeordner deines Frameworks vergleichen und den Build-Befehl prüfen [@cf-builds-troubleshoot]. |
| Unbekannte Adressen zeigen eine leere Seite statt deiner 404-Seite | `not_found_handling` ist nicht gesetzt. | `"not_found_handling": "404-page"` unter `assets` ergänzen [@cf-ssg]. |
| `npm ci` meldet, dass `package.json` und `package-lock.json` nicht zusammenpassen | Die Lock-Datei wurde nicht aktualisiert oder nicht committet. | Lokal `npm install` ausführen und `package-lock.json` committen. |
| Der Build verwendet die falsche Node.js-Version | Das Build-Image nutzt seine Standardversion. | Eine Datei `.node-version` oder `.nvmrc` anlegen oder die Build-Variable `NODE_VERSION` setzen. |
| Eine Variable fehlt beim Build | Sie wurde als Laufzeitvariable angelegt. | **Build**-Variablen gehören unter **Settings > Build**, Laufzeitvariablen unter **Settings > Variables & Secrets**. |
| Die Domain bleibt auf **Pending** | Die Nameserver wurden noch nicht geändert, oder die Umstellung läuft noch. | Nameserver beim Registrar prüfen und bis zu 24 Stunden warten [@cf-dns-setup]. |
| `ERR_TOO_MANY_REDIRECTS` | Meist widerspricht der SSL/TLS-Verschlüsselungsmodus den Weiterleitungen auf deinem eigenen Server. | Cloudflares Anleitung zu diesem Fehler folgen [@cf-redirects]. Eine Website, die ganz von einem Worker ausgeliefert wird, ist selten betroffen. |
| Es erscheint noch die alte Version | Der Browser zeigt eine zwischengespeicherte Kopie, oder der letzte Build ist fehlgeschlagen. | Mit <kbd>Ctrl</kbd>+<kbd>Shift</kbd>+<kbd>R</kbd> (macOS: <kbd>Cmd</kbd>+<kbd>Shift</kbd>+<kbd>R</kbd>) neu laden und den Status des letzten Builds prüfen. |

## Fazit

Eine Website online zu stellen heisst, Domain, DNS und Hosting zusammenzubringen, und Cloudflare kann alle drei übernehmen. Für neue Projekte empfiehlt Cloudflare Workers: Eine kleine Datei `wrangler.jsonc` beschreibt deine Website, die Verbindung mit GitHub baut und veröffentlicht jeden Push automatisch, und eine eigene Domain ist mit wenigen Klicks verbunden, sobald dein DNS bei Cloudflare liegt. Geht etwas schief, zeigen dir das Build-Protokoll und der Tab Deployments, was passiert ist, und ein Rollback holt eine frühere Version zurück, während du den Fehler behebst.
