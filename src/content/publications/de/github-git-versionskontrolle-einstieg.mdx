Kennst du Dateien wie `aufsatz-final.docx`, `aufsatz-final-2.docx` und `aufsatz-wirklich-final.docx`? Genau dieses Problem löst Versionskontrolle, und Git ist das Werkzeug, das dafür in fast jedem Softwareprojekt zum Einsatz kommt. Dieser Leitfaden erklärt zuerst die Ideen hinter Git und GitHub und führt dich dann Schritt für Schritt durch dein erstes Repository: vom ersten Commit bis zum ersten Pull Request, im Terminal und in VS Code.

Vorkenntnisse brauchst du keine. Die Beispiele verwenden ein kleines Übungsprojekt namens `my-first-website` und den Platzhalter-Benutzernamen `your-username`, den du durch deinen eigenen ersetzt.

## Wozu Versionskontrolle?

Ein **Versionskontrollsystem** zeichnet auf, wie sich Dateien im Lauf der Zeit verändern. Statt viele Kopien eines Projekts aufzubewahren, hast du einen einzigen Ordner, und das System merkt sich jeden gespeicherten Stand. Das bringt dir:

- **Eine lückenlose Geschichte.** Du siehst, was sich wann und warum geändert hat.
- **Ein Sicherheitsnetz.** Geht etwas kaputt, kehrst du zu einer Version zurück, die funktioniert hat.
- **Paralleles Arbeiten.** Du kannst eine Idee ausprobieren, ohne die funktionierende Version anzutasten, und mehrere Personen können am selben Projekt arbeiten, ohne sich gegenseitig Änderungen zu überschreiben.

## Git und GitHub: nicht dasselbe

Die beiden Namen werden oft verwechselt, bezeichnen aber Verschiedenes:

- **Git** ist ein Programm auf deinem Computer. Es erledigt die eigentliche Versionskontrolle: Es zeichnet Änderungen auf, verwaltet die Geschichte und die Branches. Git funktioniert vollständig offline [@gh-about-git].
- **GitHub** ist eine Website und ein Dienst, der Git-Repositorys online speichert. Dazu kommt alles, was man zum Teilen und Zusammenarbeiten braucht: eine Weboberfläche, Pull Requests, Issues und Zugriffsrechte.

Git lässt sich auch ohne GitHub nutzen, nur auf deinem Computer oder mit einem anderen Dienst wie GitLab. GitHub hingegen baut auf Git auf.

| Werkzeug | Was es ist | Wo es läuft | Wofür du es brauchst |
| --- | --- | --- | --- |
| Git | Programm zur Versionskontrolle | Dein Computer | Änderungen aufzeichnen und verwalten |
| GitHub | Hosting-Dienst für Git-Repositorys | github.com | Sicherung, Teilen, Pull Requests, Teamarbeit |
| GitHub Desktop | Grafische App für Git und GitHub | Dein Computer | Git nutzen, ohne Befehle zu tippen |
| VS Code | Code-Editor mit eingebauter Git-Unterstützung | Dein Computer | Code bearbeiten und Git am selben Ort nutzen |

## Die wichtigsten Begriffe

Viele Git-Begriffe sind auch im Deutschen auf Englisch üblich. Du findest sie so in Programmen, Fehlermeldungen und Anleitungen.

| Begriff | Bedeutung |
| --- | --- |
| **Repository** (Repo) | Ein Projektordner, dessen Geschichte Git verfolgt. Er enthält deine Dateien und einen versteckten Ordner `.git` mit der Geschichte. |
| **Commit** | Eine gespeicherte Momentaufnahme deiner Änderungen mit einer kurzen Beschreibung. |
| **Branch** | Ein unabhängiger Arbeitsstrang. Der Hauptbranch heisst meist `main`. |
| **Remote** | Eine Kopie des Repositorys an einem anderen Ort, meist auf GitHub. Standardmässig heisst sie `origin`. |
| **Klonen** (*clone*) | Ein Repository samt Geschichte von GitHub auf deinen Computer herunterladen. |
| **Pushen** (*push*) | Deine neuen Commits zum Remote hochladen. |
| **Pullen** (*pull*) | Neue Commits vom Remote herunterladen und in deinen Branch übernehmen. |
| **Pull Request** (PR) | Eine Anfrage auf GitHub, die Änderungen eines Branches in einen anderen zu übernehmen, mit Platz für Review und Diskussion. |

## So funktioniert Git: die drei lokalen Bereiche

Bevor du den ersten Befehl tippst, lohnt es sich zu wissen, wo deine Änderungen gerade stehen. Git kennt drei Bereiche auf deinem Computer und dazu die Kopie auf GitHub:

<GitWorkflow />

1. Du bearbeitest Dateien im **Arbeitsverzeichnis**, also im ganz normalen Projektordner.
2. Mit `git add` wählst du aus, welche Änderungen in die nächste Momentaufnahme gehören. Sie landen im **Staging-Bereich**.
3. Mit `git commit` speicherst du diese Änderungen als Commit im **lokalen Repository**.
4. Mit `git push` lädst du deine Commits auf **GitHub** hoch.

Der Staging-Bereich wirkt vielleicht wie ein Umweg, ist aber praktisch: Hast du fünf Dateien geändert und gehören nur drei davon zusammen, committest du zuerst diese drei und die anderen zwei separat. So erzählt jeder Commit eine klare Geschichte [@progit].

## Git einrichten

### 1. Git installieren

- **Windows:** Lade das Installationsprogramm von [git-scm.com](https://git-scm.com/downloads) herunter. Die Standardeinstellungen passen für den Anfang. Mitinstalliert wird der **Git Credential Manager**, der die Anmeldung bei GitHub übernimmt.
- **macOS:** Öffne das Terminal und tippe `git --version`. Ist Git noch nicht installiert, bietet macOS an, die Entwicklerwerkzeuge zu installieren; Git ist dabei.
- **Linux:** Installiere Git über die Paketverwaltung, unter Ubuntu zum Beispiel mit `sudo apt install git`.

Prüfe, ob es geklappt hat:

```bash
git --version
# git version 2.x.x
```

### 2. Git sagen, wer du bist

Jeder Commit speichert, wer ihn gemacht hat. Name und E-Mail-Adresse legst du einmal fest:

```bash
git config --global user.name "Dein Name"
git config --global user.email "du@example.com"
```

Verwende die E-Mail-Adresse deines GitHub-Kontos, damit GitHub deine Commits deinem Profil zuordnen kann. Möchtest du deine Adresse nicht öffentlich machen, findest du in den E-Mail-Einstellungen deines Kontos eine private `noreply`-Adresse [@gh-setup].

Neue Repositorys auf GitHub verwenden `main` als Namen des Hauptbranches. Damit Git auch bei Repositorys auf deinem Computer diesen Namen nimmt:

```bash
git config --global init.defaultBranch main
```

### 3. Bei GitHub anmelden

Beim ersten Push muss Git beweisen, dass du in das Repository schreiben darfst. Dein GitHub-Passwort akzeptiert GitHub dafür nicht mehr [@gh-auth]. Stattdessen empfiehlt GitHub eine dieser Varianten [@gh-credentials]:

- **Git Credential Manager** (bei Git für Windows dabei): Beim ersten Push öffnet sich ein Browserfenster, du meldest dich dort bei GitHub an, und Git merkt sich das.
- **GitHub CLI**: Installiere das Werkzeug `gh`, führe `gh auth login` aus und folge den Anweisungen.

So oder so musst du das nur einmal pro Computer erledigen.

## Tutorial 1: Dein erstes Repository

In diesem Tutorial legst du ein Repository auf GitHub an, holst es auf deinen Computer, änderst eine Datei und schickst die Änderung zurück.

### Schritt 1: Repository auf GitHub anlegen

1. Melde dich auf [github.com](https://github.com) an und wähle **New repository** (im Menü **+** oben rechts).
2. Gib einen **Namen** ein, zum Beispiel `my-first-website`. Wenn du magst, ergänzt du unter **Description** eine kurze Beschreibung des Projekts.
3. Wähle **Public** (für alle sichtbar) oder **Private** (nur für dich und eingeladene Personen).
4. Aktiviere **Add README**. Ein README ist die Startseite des Projekts, und mit ihm ist das Repository nicht leer, du kannst es also sofort klonen.
5. Wähle **Create repository**.

GitHub ist auf Englisch; die Namen der Schaltflächen stehen hier deshalb so, wie du sie auf dem Bildschirm siehst.

### Schritt 3: Repository klonen

Klicke auf den grünen Button **Code**, wähle **HTTPS** und kopiere die Adresse. Öffne dann ein Terminal in dem Ordner, in dem du deine Projekte aufbewahrst:

```bash
git clone https://github.com/your-username/my-first-website.git
cd my-first-website
```

`git clone` lädt die Dateien samt Geschichte herunter und richtet GitHub als Remote mit dem Namen `origin` ein. Git weiss jetzt, wohin es pushen soll.

<Callout type="note" title="Noch nie mit dem Terminal gearbeitet?">
  Ein Terminal ist ein Fenster, in dem du Befehle eintippst, statt zu klicken. Unter Windows nimmst du **Git Bash**; es wurde zusammen mit Git installiert und steht im Startmenü. Unter macOS öffnest du die App **Terminal**. In VS Code wählst du **Terminal > Neues Terminal**. Mit `cd` («change directory») wechselst du in einen Ordner: `cd my-first-website` führt dich in den Ordner, den `git clone` gerade angelegt hat.
</Callout>

### Schritt 4: Etwas ändern und committen

Lege im Ordner `my-first-website` mit VS Code oder einem anderen Texteditor eine Datei `index.html` an, mit beliebigem Inhalt, zum Beispiel:

```html
<!doctype html>
<html lang="de">
  <head>
    <meta charset="utf-8" />
    <title>Meine erste Website</title>
  </head>
  <body>
    <h1>Hallo Welt!</h1>
  </body>
</html>
```

Frag Git nun, was sich geändert hat. `git status` wirst du am häufigsten brauchen, und der Befehl richtet nie Schaden an:

```bash
git status
# Untracked files:
#   index.html
```

Lege die Datei in den Staging-Bereich und committe sie:

```bash
git add index.html
git commit -m "Add homepage"
```

Der Text nach `-m` ist die **Commit-Nachricht**. Formuliere sie kurz und so, dass sie beschreibt, was der Commit bewirkt: «Startseite hinzufügen», «Tippfehler im Kontaktformular korrigieren», «Farben anpassen». In vielen Projekten schreibt man sie auf Englisch, wichtig ist vor allem, dass du einheitlich bleibst. Beim Lesen der Geschichte wirst du dir später dankbar sein.

Die Geschichte zeigt dir:

```bash
git log --oneline
# 3f2c1a9 (HEAD -> main) Add homepage
# a81b0e4 (origin/main) Initial commit
```

### Schritt 5: Zu GitHub pushen

```bash
git push
```

Beim ersten Mal fragt Git nach deiner Anmeldung (siehe [Bei GitHub anmelden](#3-bei-github-anmelden)). Lade danach die Repository-Seite auf GitHub neu: `index.html` ist da, und beim letzten Commit steht deine Nachricht.

<Callout type="note" title="Du hast schon ein Projekt auf deinem Computer?">
  Statt zu klonen, kannst du auch mit einem bestehenden Ordner beginnen. Lege auf GitHub ein **leeres** Repository an (ohne README) und führe dann in deinem Projektordner diese Befehle aus:

  ```bash
  git init
  git add .
  git commit -m "Initial commit"
  git branch -M main
  git remote add origin https://github.com/your-username/my-first-website.git
  git push -u origin main
  ```

  `git init` macht den Ordner zum Repository, `git branch -M main` nennt den Branch `main`, `git remote add` verbindet ihn mit GitHub, und `-u` merkt sich die Verbindung, sodass später ein einfaches `git push` reicht.
</Callout>

## Branches: Neues ausprobieren, ohne etwas kaputtzumachen

Bisher ist jeder Commit direkt auf `main` gelandet. Für ein kleines eigenes Projekt ist das in Ordnung. Sobald eine Änderung länger dauert oder andere mitarbeiten, arbeitest du aber besser auf einem **Branch**.

Ein Branch ist ein eigener Strang von Commits. Dort kannst du experimentieren, während `main` unverändert bleibt. Ist die Arbeit fertig, führst du den Branch wieder mit `main` zusammen; das nennt man **Merge**.

<BranchMerge />

Branch erstellen und gleich zu ihm wechseln:

```bash
git switch -c add-contact-page
```

`-c` steht für «create», also erstellen. Lege jetzt eine zweite Seite an, `contact.html` (zum Beispiel eine Kopie von `index.html` mit anderer Überschrift), und committe sie wie gewohnt:

```bash
git add contact.html
git commit -m "Add contact page"
```

Alle Branches und den aktuellen (mit `*` markiert) zeigt:

```bash
git branch
# * add-contact-page
#   main
```

Hin und her wechselst du mit `git switch main` und `git switch add-contact-page`. Git tauscht dabei die Dateien in deinem Ordner aus. Wundere dich also nicht, wenn `contact.html` auf `main` verschwindet: Bis zum Merge gibt es die Datei nur auf dem Branch.

<Callout type="note" title="git switch oder git checkout?">
  Ältere Anleitungen wechseln Branches mit `git checkout`. Das funktioniert weiterhin, aber `git switch` wurde eigens für Branches eingeführt und ist leichter verständlich. Dieser Leitfaden verwendet `git switch`.
</Callout>

## Pull Requests: Änderungen vorschlagen und prüfen

Du könntest deinen Branch auch auf deinem Computer mit `git merge` zusammenführen. Auf GitHub ist ein **Pull Request** der übliche Weg: Du schlägst den Merge vor, er kann geprüft und besprochen werden, und danach wird er auf GitHub zusammengeführt [@gh-pr]. Auch wenn du allein arbeitest, lohnt sich die Gewohnheit: Du siehst an einem Ort alle Änderungen einer Arbeit, bevor sie in `main` landen.

### Schritt 1: Branch pushen

```bash
git push -u origin add-contact-page
```

Beim ersten Push eines neuen Branches braucht es `-u origin <branch-name>`, damit Git weiss, wohin er auf GitHub gehört. Danach reicht `git push`.

### Schritt 2: Pull Request öffnen

Auf GitHub erscheint ein gelbes Banner mit **Compare & pull request**. (Alternativ öffnest du den Tab **Pull requests** und wählst **New pull request**.)

1. Prüfe oben die beiden Branches: **base** ist das Ziel (`main`), **compare** dein Branch (`add-contact-page`).
2. Schreibe einen Titel und eine kurze Beschreibung: Was ändert sich, und warum?
3. Wähle **Create pull request**.

Die Seite des Pull Requests hat mehrere Tabs. **Files changed** zeigt jede geänderte Zeile: grün für hinzugefügte, rot für entfernte. Hier können andere auch einzelne Zeilen kommentieren.

Passt alles, wählst du **Merge pull request** und bestätigst. Anschliessend bietet GitHub an, den Branch zu löschen (**Delete branch**). Das ist unbedenklich, denn seine Commits gehören jetzt zu `main`.

### Schritt 4: Deinen Computer aktualisieren

Der Merge ist auf GitHub passiert; dein lokaler `main` weiss davon noch nichts:

```bash
git switch main
git pull
git branch -d add-contact-page
```

`git pull` holt die zusammengeführten Commits auf deinen Computer, und `git branch -d` löscht die lokale Kopie des Branches, die du nicht mehr brauchst.

## Merge-Konflikte

Manchmal ändern zwei Branches **dieselben Zeilen** derselben Datei. Git kann nicht entscheiden, welche Fassung stimmt, hält an und überlässt dir die Entscheidung. Das nennt man **Merge-Konflikt**. Er kann bei `git merge` oder `git pull` auftreten oder in einem Pull Request. Klingt dramatisch, gehört aber ganz normal zur Arbeit mit Git [@gh-conflicts].

Git markiert die betroffene Stelle direkt in der Datei:

```text
<h1>
<<<<<<< HEAD
Willkommen auf meiner Website
=======
Hallo und herzlich willkommen!
>>>>>>> add-contact-page
</h1>
```

- Zwischen `<<<<<<< HEAD` und `=======` steht die Fassung deines aktuellen Branches.
- Zwischen `=======` und `>>>>>>>` steht die Fassung des anderen Branches.

Zum Lösen bearbeitest du die Datei so, dass sie den gewünschten Text enthält, und **löschst alle drei Markierungszeilen**. Dann speicherst du und schliesst den Merge ab:

```bash
git add index.html
git commit --no-edit
```

`--no-edit` übernimmt die Commit-Nachricht, die Git für den Merge bereits vorbereitet hat. Ein einfaches `git commit` würde zuerst einen Texteditor für die Nachricht öffnen, was verwirrend sein kann, wenn du ihn nicht kennst.

In einem Pull Request auf GitHub lassen sich einfache Konflikte auch im Browser lösen, über den Button **Resolve conflicts**.

| **Änderungen synchronisieren** (*Sync Changes*) | `git pull` und `git push` | Lädt Commits herunter und hoch |
| Branch-Name in der Statusleiste | `git switch` | Klick zum Wechseln oder Erstellen eines Branches |
| **Branch veröffentlichen** bzw. **Verzweigung veröffentlichen** (*Publish Branch*) | `git push -u origin <branch>` | Pusht einen neuen Branch zum ersten Mal |

## Gute Gewohnheiten

### Dateien mit `.gitignore` aus Git heraushalten

Manche Dateien gehören nicht in ein Repository: installierte Pakete (`node_modules/`), Build-Ergebnisse (`dist/`), Systemdateien (`.DS_Store`) und vor allem **Passwörter, API-Schlüssel und andere Geheimnisse**. Trage sie in eine Datei namens `.gitignore` im Projektordner ein, dann ignoriert Git sie [@gh-ignore]:

```text
# Abhängigkeiten und Build-Ergebnisse
node_modules/
dist/

# Lokale Einstellungen und Geheimnisse
.env

# Systemdateien
.DS_Store
Thumbs.db
```

Beim Anlegen eines Repositorys auf GitHub kannst du eine fertige `.gitignore`-Vorlage für deine Programmiersprache auswählen.

### Klein und oft committen

Ein guter Commit enthält **eine** zusammengehörige Änderung und eine klare Nachricht. Kleine Commits sind leichter zu verstehen, zu prüfen und nötigenfalls rückgängig zu machen. Committe, wenn etwas funktioniert, nicht erst am Ende des Tages.

## Häufige Fehler und ihre Lösung

Git gibt seine Meldungen meist auf Englisch aus. Die Tabelle zeigt sie deshalb im Original.

| Meldung oder Problem | Was sie bedeutet | Was du tust |
| --- | --- | --- |
| `Author identity unknown` | Git kennt deinen Namen und deine E-Mail-Adresse noch nicht. | Die beiden Befehle `git config --global` aus dem Abschnitt zur Einrichtung ausführen. |
| `fatal: not a git repository` | Das Terminal befindet sich nicht in einem Repository-Ordner. | Mit `cd` in den Projektordner wechseln oder bei einem neuen Projekt `git init` ausführen. |
| `Support for password authentication was removed` oder `Authentication failed` | Du hast versucht, dich mit deinem GitHub-Passwort anzumelden. | Stattdessen über den Git Credential Manager oder `gh auth login` anmelden. |
| `! [rejected] main -> main (fetch first)` | Auf GitHub gibt es Commits, die dein Computer noch nicht hat. | `git pull` ausführen, allfällige Konflikte lösen, dann erneut `git push`. |
| `CONFLICT (content): Merge conflict in …` | Zwei Branches haben dieselben Zeilen geändert. | Datei bearbeiten, Markierungen entfernen, dann `git add` und `git commit --no-edit`. |
| `src refspec main does not match any` | Es gibt noch keinen Commit, oder dein Branch heisst anders (oft `master`). | Einen ersten Commit machen oder den Branch mit `git branch -M main` umbenennen. |
| `node_modules` oder andere grosse Ordner wurden committet | Sie fehlten in der `.gitignore`. | In die `.gitignore` eintragen, dann `git rm -r --cached node_modules` ausführen und committen. |
| Ein Passwort oder API-Schlüssel wurde gepusht | Er steht jetzt in der Geschichte, auch wenn du die Datei löschst. | **Das Geheimnis sofort ändern oder widerrufen**, dann mit GitHubs Anleitung aus der Geschichte entfernen [@gh-sensitive]. |

<Callout type="warning" title="Geheimnisse verschwinden nicht durch Löschen">
  Ein Commit ist eine dauerhafte Momentaufnahme. Pushst du eine Datei mit einem Passwort oder Schlüssel und löschst sie im nächsten Commit, steht sie trotzdem in der Geschichte, und alle mit Zugriff können sie finden. Betrachte ein gepushtes Geheimnis als kompromittiert: zuerst ersetzen, dann aufräumen.
</Callout>

## Befehlsübersicht

| Befehl | Was er macht |
| --- | --- |
| `git clone <url>` | Kopiert ein Repository von GitHub auf deinen Computer |
| `git status` | Zeigt geänderte, gestagte und neue Dateien |
| `git add <datei>` / `git add .` | Stagt eine Datei / alle Änderungen im Ordner |
| `git commit -m "Nachricht"` | Speichert die gestagten Änderungen als Commit |
| `git log --oneline` | Zeigt die Geschichte, ein Commit pro Zeile |
| `git push` | Lädt deine Commits auf GitHub hoch |
| `git pull` | Holt neue Commits von GitHub und führt sie zusammen |
| `git switch -c <name>` | Erstellt einen neuen Branch und wechselt zu ihm |
| `git switch <name>` | Wechselt zu einem bestehenden Branch |
| `git branch` | Listet die Branches; `*` markiert den aktuellen |
| `git merge <name>` | Führt einen anderen Branch in den aktuellen zusammen |
| `git restore <datei>` | Verwirft nicht committete Änderungen an einer Datei |
| `git restore --staged <datei>` | Nimmt eine Datei aus dem Staging-Bereich, die Änderungen bleiben |
| `git diff` | Zeigt nicht gestagte Änderungen Zeile für Zeile |

## Fazit

Git zeichnet die Geschichte deines Projekts auf deinem Computer auf; GitHub speichert sie online und macht die Zusammenarbeit einfach. Der Alltag besteht aus einem kurzen Kreislauf: Dateien ändern, `git add`, `git commit`, `git push`. Mit Branches arbeitest du an Neuem, ohne die funktionierende Version zu gefährden, und Pull Requests geben jeder Änderung einen Ort, an dem sie vor dem Merge geprüft wird. Ob du Befehle tippst oder in VS Code klickst, die Ideen bleiben dieselben. Hast du sie einmal verstanden, ist der Rest Übung.
